# Nimbus UPS Bar QA report, 2026-10-11

2026-10-11 · Niels Joubert

> **Status:** every finding below was fixed on 2026-10-11 in
> [PR #14](https://github.com/njoubert/nimbus-ups-bar/pull/14), each with the regression test the
> last section asks for; the owner's checklist items went into the README.

## Summary

The core promise holds on this desk, but two defects can stall or misdirect the guard at the moment
it matters, and four more weaken it over weeks of unattended running. Every force-unmount of the
Flitslig RAID through the app's own Disk Arbitration path succeeded (open files, a working directory,
an mmap, a writing app, and a 24 GB write in flight), and two real drills ran the full state machine
against the real volume exactly as the policy said. Both unit suites pass (77 guard scenarios, 68
platform checks), the HID path returned 170 of 170 reads, and the running copy's memory was flat over
48 minutes.

**Fix first**

1. **Asking a mis-identified "app" to quit freezes the whole app for 2 minutes** on the main thread
   (an AppleScript fallback in `Holders.requestQuit`). Verified live: a Homebrew `python3` holding a
   file on Flitslig blocked the call for exactly 120 s, it returned `true`, and the process kept the
   file. During the freeze there are no ticks, no hard limit, no menu.
2. **Any process whose executable lives inside an `.app` bundle counts as an app**, so command-line
   tools become "apps" the soft stage waits for and tries to quit: Homebrew `python3` shows as
   "Python", and the Xcode toolchain that `/usr/bin/git`, `swift` and `clang` run from would resolve
   to Xcode itself and send Xcode a quit event.
3. **A relaunch forgets which volumes the guard unmounted**, so after a crash-restart during an outage
   the drive is not remounted when power returns.
4. **The sleep action goes ahead after 60 s with a protected volume still mounted**; sleep does not
   unmount anything, so the enclosure would die with the volume mounted when the UPS runs out.
5. **A forced-unmount stage with no time condition can never fire while the UPS's figures are
   missing**, and the UPS's own low-battery flags are not a trigger. The owner's current
   configuration has the time condition off.
6. **A stuck USB HID read is never recovered**: the read queue is serial, so every later read waits
   behind the stuck one until the app is relaunched.

| Severity | Correctness and durability | Displayed information |
| --- | --- | --- |
| High | 2 | 0 |
| Medium | 4 | 2 |
| Low | 3 | 4 |

What the owner runs today is the development bundle from `dist/debug`, hand-launched, with no launchd
agent and a policy whose forced unmount depends entirely on the charge and runtime figures. Until the
items above land, the protection is real during a plain outage but not durable across a crash, a
stuck USB read or a stubborn command-line holder.

Everything ran on the owner's desk on 2026-10-11 between 16:40 and 17:30 against commit `bfd1e62`
(main), with the owner's hand-launched development copy left running throughout. The owner authorised
unmounting the drives for this run; no app of the owner's was quit, and the only volume touched was
Flitslig, which was empty of holders before every real unmount.

## Findings: correctness and durability of the promise

Ranked by how directly each can lose data or leave the guard not guarding. "Verified" means
reproduced on the desk; "scenario" means shown against the fake desk with the real `OutageGuard`;
"code" means found by reading and not reproducible without a fault.

### H1. Asking a mis-identified app to quit freezes the app for 2 minutes (verified)

`Holders.requestQuit` falls back to `NSAppleScript("tell application id … to quit")` when neither
`runningApplications(withBundleIdentifier:)` nor `NSRunningApplication(processIdentifier:)` knows the
holder. Compiling that script makes AppleScript fetch the target's scripting terminology over an
Apple event, and a process that does not speak Apple events never answers, so the call sits in
`AESendMessage` until the two-minute Apple event timeout. The sampled stack: `Holders.requestQuit` →
`NSAppleScript compileAndReturnError` → `GetAppTerminology` → `AESendMessage` → `mach_msg`.

- Reproduced with a Homebrew `python3` holding a file by mmap: the call started 17:11:27.44, returned
  17:13:27.66 (120.2 s), returned `true`, and the process was still alive and still holding the file.
  Nothing was logged, because `true` means "sent".
- The guard calls this synchronously from `evaluate()` on the main thread. For those two minutes
  nothing ticks, the hard limit is not evaluated, Disk Arbitration callbacks queue, HID results queue,
  the menu is dead. With the default policy the soft stage starts at 2 min and the hard limit at
  5 min, so one such holder eats two of the three minutes of margin; the owner's 1 min quit timeout
  is simply late.
- One freeze per distinct bundle id per outage (`asked` is keyed on `appKey`).

Fix: never call `NSAppleScript` on the main thread, and not at all for quitting. A holder
LaunchServices does not know is not an app anyone can quit: log "cannot ask X to quit: not a running
application" and treat it as a daemon. If the fallback must stay, run it off the main thread with
`AESendMessage`'s own timeout set to a few seconds.

### H2. Any executable inside an `.app` bundle is an "app" (verified)

`Holders.describe` takes the first `.app/` component of the executable path as the owning app. That
is right for a renderer helper inside Brave and wrong for every command-line tool that happens to live
in a bundle.

- `python3` from Homebrew runs from `Python.framework/…/Resources/Python.app/Contents/MacOS/Python`;
  the menu shows "Python" as an app holding Flitslig, the soft stage waits for it, and asking it
  triggers H1.
- On this Mac `xcode-select` points at Xcode.app, so `/usr/bin/git`, `swift`, `clang` and the rest
  exec binaries under `/Applications/Xcode.app/…`. A `git` or a build writing to the RAID would
  resolve to Xcode (bundle id `com.apple.dt.Xcode`); with Xcode running, the guard would send Xcode a
  quit event, which is the owner's IDE and not the holder.
- Right now 24 running processes on this machine live inside an `.app` but are not LaunchServices
  applications (Claude, Dropbox, Spotify and 1Password helpers among them). Most resolve to a running
  parent with the same bundle id and would quit the parent, which is the intended behaviour for
  helpers. The dangerous cases are the ones with no running parent (H1) and the ones whose parent is
  the wrong app (Xcode).

Fix: an app is a process LaunchServices knows. Use `NSRunningApplication(processIdentifier:)` as the
primary test; take the bundle id and name from it; walk to the outer bundle only to find the parent of
a helper whose own bundle id is not a running application. Everything else is "other". Add fixture
cases for `Python.app` inside a framework and for a toolchain path inside Xcode.app.

### M1. What the guard unmounted is forgotten on relaunch (scenario S1)

Only `outageStartedAt` is persisted. A copy relaunched mid-outage (the agent's crash restart, an
update, toggling *Run in Background*) resumes the clock but has an empty `unmountedByGuard`, so when
power returns nothing is remounted and the outage menu's *Remount Now* never appears. The volume's own
submenu still offers *Mount*, but the README promises the remount. The same relaunch also re-asks
every app (scenario S8) because `asked` is not carried either.

Fix: persist the unmounted UUIDs (and the asked bundle ids) next to `outageStartedAt`, hand them to
the guard at launch as it does `resumeElapsed`, and drop them with a line reading on a clean start.

### M2. Sleep proceeds with a protected volume still mounted (scenario S6)

`powerDownWait` (60 s) lets the power-down action run even when a volume refused every unmount. For
*shut down* that is defensible: macOS flushes and unmounts on the way down. For *sleep* it is not:
sleep leaves the volume mounted and dirty, the Mac sleeps on UPS power, and when the UPS dies the
enclosure dies with the volume mounted. That is the one outcome the app exists to prevent, reached by
the app's own action. Low likelihood (force unmount has to keep failing) but the worst possible
impact.

Fix: for `.sleep`, never perform while a protected volume is mounted; keep retrying every 10 s and
stay awake. Keep the 60 s rule for `.shutDown` only, and say so in the Settings hint.

### M3. Policies that depend on the UPS's figures alone can never fire, and the UPS's own low-battery flags are ignored (scenario S5, S7)

With the forced unmount set to runtime and charge only (the owner's configuration since 2026-10-11
13:26: `hardTimeOn = 0`), a reading with no charge and no runtime leaves the guard in *holding* for
the whole outage. Today the figures come from two sources (HID, then IOKit's minutes), so both would
have to fail, but a stuck HID read (M4) removes one of them. Separately, the UPS declares its own low
battery through `BelowRemainingCapacityLimit` (10 %) and `RemainingTimeLimitExpired` (5 min);
`Trigger` ignores both and only `ShutdownImminent` forces. A policy with thresholds below the UPS's
would ride through the UPS's own alarm.

Fix: treat the two limit flags like `shutdownImminent`, an always-on backstop independent of policy.
In Settings, warn when the forced unmount has no time condition, or have `normalized` keep a long time
backstop (an hour) whenever the time condition is off.

### M4. A stuck HID read is never recovered (code)

`UPSMonitor.readHID` dispatches every read onto one serial queue (`hidQueue`). When a read wedges
inside `IOHIDDeviceGetValueWithOptions`, the monitor abandons it after 10 s and starts another, but
the new block waits behind the stuck one forever. `hidAbandoned` climbs every 10 s, `hidReadAt` goes
stale, the merge falls back to IOKit (state, charge, runtime in minutes) and the health line warns.
Load, voltages, the limits and `shutdownImminent` are gone until a relaunch, and the agent only
restarts a crashed copy, never a wedged one. The CLAUDE.md notes that a wedge was already seen once.

Fix: after the second consecutive abandoned read, close and re-open the `IOHIDDevice` (or recreate
the manager) on a fresh queue; count recoveries in the Inspector. A concurrent queue with one read in
flight at a time, dropping the stuck block's result by sequence, also works.

### M5. Stages fire while mains is back but not yet trusted (scenario S2, S3)

During the 30 s stand-down after a clean power return the clock keeps running and the stages keep
firing: mains back at 1:55 and the soft stage due at 2:00 asks Lightroom to quit and unmounts the
volume while the power is already on; mains back at 4:55 with the hard limit at 5:00 force-unmounts
at 5:00. Both remount 30 s later. The power-down trigger already respects `standingDown`; the stages
do not. The brownout case the hysteresis was built for is unaffected if only the time conditions
pause, because a brownout keeps bringing the battery readings back.

Fix: while standing down, defer the time conditions and keep the charge and runtime ones, matching
the power-down trigger.

### M6. App Nap is not opted out (unverified)

Nothing in the sources or `Info.plist` holds an activity or sets `LSAppNapIsDisabled`, so macOS may
nap the process when it has been idle, coalescing its 2 s timer. The power-source run-loop source
would still wake it at the transfer, but every tick after that is the timer. Whether this copy
actually naps could not be checked without root; Activity Monitor's App Nap column would show it.

Fix: hold `ProcessInfo.processInfo.beginActivity(options: .userInitiatedAllowingIdleSystemSleep,
reason:)` for the life of the process (it disables App Nap without touching idle sleep, which the
guard's own assertion manages), or set `LSAppNapIsDisabled` in the bundle's Info.plist.

### L1. The hard stage is not latched on charge or runtime (scenario S4)

With a charge-only hard limit and a failing unmount, a gauge bouncing 49 → 51 → 49 flips the phase
hard → holding → hard, pauses the retries while above the line, and makes the headline flip between
"Unmounting" and "On battery". The soft stage latches (`softSince`); the hard stage should too.

### L2. The holder list only sees the current user's processes (verified)

`proc_listpidspath` without root lists only processes of the calling user. Scanning `/` listed 731
processes, all the owner's; `launchd`, `mds_stores`, `smbd` and Backblaze's `bztransmit` (all root,
all with files open on `/`) were absent. For the guard this is harmless because daemons are never
waited for and every unmount is forced; the display consequences are under T1.

### L3. A forced unmount leaves SMB clients' mounts of the volume stale (verified, by the owner)

The server side recovers on its own: after every remount `smbd` was still exporting Flitslig-Drop,
the share path existed, and the Mac Studio's TCP session (10.1.0.1:50897) stayed established. The
client side does not: the Mac Studio had the volume mounted over SMB (as an admin user macOS lists
every mounted volume, not only the share points), and after the unmount and remount underneath it
Finder there reported "The operation can't be completed because the original item for 'Flitslig'
can't be found" (seen about 17:40). The client's handles point at a filesystem instance that no
longer exists, and Apple's SMB client does not reconnect because the session never dropped. The cure
on the client is to eject the stale mount and connect again; the owner did that on the Mac
Studio and it worked. This answers the README's open item on
the SMB client side, and it will happen after every real outage: the Mac Studio's mount of Flitslig
dies when the guard unmounts and does not come back when the guard remounts.

Fix: say so in the README ("after an outage, reconnect from other Macs") and in the "Power restored"
notification. Optionally drop the stale sessions on remount so clients reconnect cleanly
(`launchctl kickstart -k system/com.apple.smbd` needs root, so that would be a documented step, not
an action of the app).

## Findings: correctness and trustworthiness of what is displayed

Every figure the menu, `--print` and the Inspector showed matched the raw sources in the live probes:
charge 100 %, runtime 1 h 38 min (5900 s from HID, 98 min from IOKit), load 54 W at 5 % of 1000 W,
121 V in and out, battery 27.1 V on a 24 V pack, transfer window 100 to 139 V, self-test passed,
freshness "read 1 s ago over USB HID". The problems are in what is left out or said too soon.

### T1. "Nothing has files open on it" can be false (medium, verified)

Because the holder scan sees only the owner's processes (L2), the volume submenu, the Inspector's
*Others holding files* and the log's "(ignoring smbd)" can never show `smbd` serving the
Flitslig-Drop share, Backblaze's `bztransmit`, Spotlight's `mds_stores` or Time Machine. A Backblaze
upload or an SMB client mid-copy reads as an idle volume. The unmount is forced either way, so the
risk is to the owner's judgement, not the data: the menu says nothing is using the drive while the
Mac Studio may be writing to it.

Fix: say what the list is. "Your processes with files open" and a footnote "system daemons and other
users' processes are not visible without root"; the README's "native lsof" sentence needs the same
caveat.

### T2. Denied notifications are silent (medium, code)

`Notifications.requestAuthorizationIfNeeded` stores `ok` and logs only an error object; a plain
denial is swallowed. The development bundle was denied on 2026-10-10 17:48 ("Notifications are not
allowed for this application" is in the log, from the request's error that time). Nothing in Health,
the headline or the General pane tells the owner that the "Power outage" and "Unmounting now" banners
will never appear. For a guard meant to run unattended, a notification channel that is off is a fault
worth a yellow dot.

Fix: a health note when `authorized == false` or `notificationsEnabled` is off, a log line at launch,
and the status in Settings › General with a button to System Settings.

### T3. Command-line tools shown as apps (low, verified)

The same root cause as H2: the Flitslig row read "mounted · Python" with a `python3` script holding a
file, and its submenu offered to quit it. A `git` or a build would show as "Xcode". Fixed by H2.

### T4. The command-line snapshot's Guard page contradicts its UPS page (low, verified)

`--inspect-json` and an Inspector opened before the guard arms show *UPS present: no* and *Phase:
Line power* while the UPS and Power Source pages show the UPS present and healthy, because the
unarmed guard has never been ticked. The *Guarding: no* row explains it, but a reader pasting the
JSON into an agent gets a contradiction. Fix: in the unarmed state show "—" for the guard's live
rows, or tick the status once from the current reading without arming.

### T5. "No load on the battery outlets" fires on one reading (low, from the project's own notes)

The 0 % load warning turns the bolt yellow on a single read; the CLAUDE.md records a first read of
the day at 0 % and 190 min. Fix: require the condition to hold for two reads or a minute, as the
stale-HID warning already does.

### T6. Countdown wording (cosmetic)

`Duration.countdown` writes "60 min" and "90 min" where `Duration.text` writes "1 h" and
"1 h 30 min". Only the menu bar uses the former. Either is fine; one of them should be the rule.

Not a finding, but worth knowing: the SMB share point survived every unmount and remount (the Mac
Studio's TCP session stayed established throughout, though its mount went stale, see L3), and the
owner's running copy logged nothing and remounted nothing when QA unmounted the volume under it, which
is the right behaviour for a volume it did not unmount.

## Not tested, and what this session changed on the desk

The items below could not be exercised from a terminal without a hand at the desk or without
breaking the ground rules. The owner's keyboard checklist in the README still stands for all of them.

- **A real transfer to battery** (plug pull), the USB cable pulled mid-outage, and mains flapping. The
  two live outages in the log and the fake-desk scenarios are the evidence for these paths.
- **The enclosure losing power and coming back**: Disk Arbitration's disappeared and reappeared
  callbacks on a real detach, the RAID set reassembling, and macOS auto-mounting the volume.
  `VolumeRegistry.update(gone:)` relies on the disappeared callback still carrying a mountable
  description with the UUID; that is likely but unverified.
- **Sleep and shutdown** (`--after-safe`), including whether the hardened-runtime bundle gets an
  Automation prompt for `loginwindow`.
- **Agent registration, crash restart and the enable/disable hand-over**: installing is the owner's
  call.
- **The self-test**: the owner's to run.
- **Whether the running copy naps** (M6) and whether notifications are currently allowed for the
  development bundle (T2): both need root or the UI.
- **A HID read that wedges** (M4): no way to make the UPS misbehave on demand.
- **The Settings and Inspector windows on screen**: `--dump-settings` and `--dump-inspector` open
  windows on the owner's display, so they were not run; the Inspector's data was checked through
  `--inspect-json` instead.
- **A second external drive**: the LEICA M card seen on 2026-10-11 15:12 was not attached. Everything
  above ran against one volume.

**Side effects of this session, all undone**

- A scratch folder `/Volumes/Flitslig/.nimbus-qa/` held a small text file and, twice, a large
  zero-filled file (2 GB, then 24 GB). Removed.
- Flitslig was force-unmounted five times (17:14, 17:16, 17:20, 17:22, 17:24) for between 7 s and
  40 s each, and remounted each time through the app's code. The Flitslig-Drop share was unreachable
  for those windows. The Mac Studio's SMB session stayed up at the TCP level, but its mount of
  Flitslig went stale (L3) and had to be ejected and reconnected by hand; the owner met Finder's
  "original item can't be found" at about 17:40.
- The fake app was first launched through LaunchServices, which made macOS block it inside `open()`
  with a removable-volume permission prompt; the process was killed, which dismisses the prompt. If a
  stale "QAHolder would like to access files on a removable volume" dialog is still on screen, it can
  be denied. QAHolder lives only in the session scratch directory.
- One `lsof +D` over the whole volume was started by mistake and killed after about two minutes.
- Nothing was committed, installed or registered; no preference of the owner's copy was changed; the
  owner's copy ran untouched throughout (pid 69670, started 16:38).

## Recommended additions to the suites and the checklist

Each fix above should land with the scenario that would have caught it, per the project's own rule.
These are the ones the current suites lack.

**`Tests/UpsGuardCoreTests/GuardTests.swift`**

- [ ] Relaunch while safe (`resumeElapsed` set, volume unmounted) followed by line power: the volume
      is remounted and apps are not re-asked (M1).
- [ ] Sleep trigger with an unmount that keeps failing: no `perform(.sleep)` while a volume is
      mounted; the same scenario with `.shutDown` still goes after 60 s (M2).
- [ ] A reading with `chargePercent == nil` and `runtimeSeconds == nil` under a hard trigger without
      a time condition: something still forces (M3), and `belowCapacityLimit` /
      `runtimeLimitExpired` force like `shutdownImminent` (M3).
- [ ] Mains back 5 s before the soft stage and 5 s before the hard limit: no quit and no force during
      the stand-down; charge and runtime conditions still fire during it (M5).
- [ ] Charge-only hard limit with a bouncing gauge and a failing unmount: the phase stays `hard` and
      retries continue (L1).

**`Tests/NimbusUpsBarKitTests/HoldersTests.swift`**

- [ ] `Python.app` inside `Python.framework` is not an app (H2).
- [ ] A toolchain binary under `/Applications/Xcode.app/Contents/Developer/…` is not an app, and is
      not Xcode (H2).
- [ ] A helper `.app` whose outer bundle is a running application still resolves to that application
      (the Brave case must keep working).
- [ ] `requestQuit` on a holder LaunchServices does not know returns within a bounded time and never
      calls `NSAppleScript` (H1). This needs a seam: inject the "running applications" lookup so the
      test can hand back nothing.

**`Tests/NimbusUpsBarKitTests/HealthTests.swift`**

- [ ] A notifications-denied item (T2); the 0 % load warning only after two readings (T5).

**Monitor** (no suite today; worth one)

- [ ] `UPSMonitor` with a fake HID whose `fetch` never returns: the second abandoned read reopens the
      device and the third read succeeds (M4).

**The owner's checklist (README › Before relying on it unattended)**

- [ ] Open Activity Monitor's App Nap column after the app has sat idle for ten minutes (M6).
- [ ] Check System Settings › Notifications for the installed bundle after the first launch from
      `/Applications` (T2).
- [ ] Pull the enclosure's power once with the volume unmounted by the guard, then restore it: confirm
      the disappeared and reappeared callbacks and the auto-remount in the log.
